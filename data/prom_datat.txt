# ЦЕЛЬ
Сгенерируй реалистичный синтетический набор данных для PostgreSQL-БД «Цифровое портфолио школьника УУНиТ» в виде 11 CSV-файлов, готовых к импорту. Данные нужны университету для аналитики: из каких школ приходят потенциальные абитуриенты, какие достижения и результаты они имеют, какие направления УУНиТ их интересуют, для каких направлений учитываются их достижения, какие школы наиболее активны. В базе только школьники. Студентов нет, поля person_type нет.

# РЕЖИМ РАБОТЫ
- Код, SQL и псевдокод в чат не выводить. Не заменять данные многоточиями, «остальные аналогичны» или примерами. Не добавлять столбцы вне схемы.
- Сначала определи, доступны ли инструменты выполнения кода и создания файлов. Если доступен Python, контейнер, файловая система или иной способ создавать скачиваемые файлы, ОБЯЗАТЕЛЬНО используй его и выполняй Режим А. Не выбирай Режим Б только потому, что пользователь не приложил готовые файлы или потому, что CSV нельзя показать непосредственно в сообщении.
- Режим А — ОСНОВНОЙ И ОБЯЗАТЕЛЬНЫЙ ПРИ НАЛИЧИИ СРЕДЫ: сгенерируй полный набор данных во внутренних вычислениях; создай 11 отдельных CSV-файлов в текущем сеансе; создай ZIP-архив; открой/прочитай созданные файлы обратно и выполни проверки по фактическому содержимому; приложи ссылки на скачивание всех CSV и ZIP в финальном ответе. Если возможно, создай также README_import.md с инструкцией импорта.
- При создании CSV используй UTF-8 без BOM, LF, запятую как разделитель, точные заголовки, корректное экранирование CSV и пустую строку для NULL. Все данные должны быть записаны в файлы полностью, а не только частично. Каждая таблица должна иметь все строки, предусмотренные объёмами и правилами.
- Перед финальным ответом проверь для каждого файла: он существует; размер больше нуля; файл открывается как UTF-8; заголовок в точности соответствует схеме; каждая строка корректно разбирается CSV-парсером; число строк данных соответствует фактически сгенерированному количеству. Также проверь, что ZIP существует и содержит все 11 CSV с правильными именами.
- Если при проверке найдены нарушения, исправь исходные данные, пересоздай затронутые CSV и ZIP и повтори проверки. Не выдавай непроверенную или заведомо неполную версию как готовую.
- Режим Б — ТОЛЬКО ЕСЛИ в текущем сеансе действительно отсутствуют любые средства создания и прикрепления файлов: тогда выведи CSV-блоки с именем файла, партиями по 150–250 строк, в порядке раздела 5. После каждой партии сообщай таблицу, сколько строк создано, сколько осталось и что генерируется следующим. На «Продолжай» продолжай с того же места, не меняя уже созданное и не начиная нумерацию заново. Если Режим Б неизбежен, прямо сообщи, что скачать CSV-файлы как вложения в этой среде не удалось; не имитируй наличие файлов.
- МАСШТАБ = 1.0 (пользователь может изменить). Если МАСШТАБ < 1, умножь на него количества person, achievement, achievement_document, change_log, person_direction_interest и achievement_direction; справочники (school, study_direction, achievement_kind, event_type, event) остаются полными. Пропорции и все правила сохраняются. Сообщи, какой масштаб применён. Без явного указания МАСШТАБ сокращать объём нельзя.
- Скрытые параметры (темы видов и мероприятий, число достижений на человека) в CSV не попадают. В Режиме А храни их во внутренних структурах данных для обеспечения согласованности. В Режиме Б после соответствующих таблиц выведи их отдельным «служебным реестром» (не CSV) и используй во всех следующих партиях без изменений.
- Если два требования противоречат друг другу, коротко назови конфликт и выбери вариант, наиболее близкий к смыслу задачи.
- Не утверждай, что проверка прошла, если она фактически не выполнена. Статистику считай только по созданным данным.
- Не задавай уточняющих вопросов, если можно выполнить задачу с указанными параметрами. При МАСШТАБ=1.0 создай весь объём из раздела 2.

# 1. ЭТАЛОННАЯ СХЕМА (NN = NOT NULL; в ответ не выводить)
school(school_id SERIAL PK, name VARCHAR(150) NN, city VARCHAR(80) NN, school_type VARCHAR(10) NN IN ('secondary','lyceum','gymnasium','boarding'), UNIQUE(name,city))

person(person_id SERIAL PK, full_name VARCHAR(150) NN, email VARCHAR(255) NN UNIQUE, phone VARCHAR(12) NN UNIQUE CHECK(phone ~ '^\+7[0-9]{10}$'), birth_date DATE NN, school_id INT NN FK→school ON DELETE RESTRICT, registration_date DATE NN DEFAULT CURRENT_DATE, CHECK(registration_date >= birth_date + INTERVAL '10 years'))

study_direction(direction_id SERIAL PK, code VARCHAR(8) NN UNIQUE формат NN.NN.NN, name VARCHAR(150) NN, institute VARCHAR(100) NN, degree_level VARCHAR(10) NN IN ('bachelor','specialist'))

person_direction_interest(person_id INT NN FK→person CASCADE, direction_id INT NN FK→study_direction CASCADE, priority SMALLINT NN BETWEEN 1 AND 5, added_date DATE NN, PK(person_id,direction_id), UNIQUE(person_id,priority))

achievement_kind(kind_id SERIAL PK, name VARCHAR(150) NN UNIQUE, category VARCHAR(10) NN IN ('olympiad','hackathon','science','sport','creative','volunteer','education'), base_points INT NN BETWEEN 0 AND 100, valid_from TIMESTAMP NN DEFAULT CURRENT_TIMESTAMP)

event_type(event_type_id SERIAL PK, name VARCHAR(150) NN UNIQUE, event_format VARCHAR(11) NN IN ('olympiad','hackathon','conference','contest','competition'), description VARCHAR(300) NN, is_team BOOLEAN NN, is_individual BOOLEAN NN, prize_places SMALLINT NN BETWEEN 0 AND 10, duration_days SMALLINT NN BETWEEN 1 AND 60, CHECK(is_team OR is_individual))

event(event_id SERIAL PK, name VARCHAR(200) NN, event_type_id INT NN FK→event_type RESTRICT, event_level VARCHAR(13) NN IN ('school','municipal','regional','national','international'), event_date DATE NN >= 2015-01-01, UNIQUE(name,event_date))

achievement(achievement_id SERIAL PK, person_id INT NN FK→person CASCADE, kind_id INT NN FK→achievement_kind RESTRICT, event_id INT NN FK→event RESTRICT, achieved_date DATE NN >= 2015-01-01, place SMALLINT NULL (NULL или 1..10), points_awarded INT NN >=0, status VARCHAR(11) NN DEFAULT 'submitted' IN ('submitted','confirmed','rejected'), created_at TIMESTAMP NN DEFAULT CURRENT_TIMESTAMP, UNIQUE(person_id,event_id,kind_id))

achievement_direction(achievement_id INT NN FK→achievement CASCADE, direction_id INT NN FK→study_direction CASCADE, relevance VARCHAR(6) NN IN ('high','medium'), bonus_points SMALLINT NN BETWEEN 1 AND 10, counted_from DATE NN, PK(achievement_id,direction_id)). Смысл связи: «достижение учитывается для направления» (индивидуальные достижения при поступлении).

achievement_document(document_id SERIAL PK, achievement_id INT NN FK→achievement CASCADE, doc_type VARCHAR(11) NN IN ('diploma','certificate','reference','link'), doc_number VARCHAR(40) NULL, issue_date DATE NN, file_url VARCHAR(300) NN начинается с https://)

change_log(log_id SERIAL PK, achievement_id INT NN FK→achievement CASCADE, old_status VARCHAR(11) NULL, new_status VARCHAR(11) NN, changed_at TIMESTAMP NN, actor_role VARCHAR(9) NN IN ('owner','moderator','system'), note VARCHAR(200) NULL, old_status и new_status различаются; значения статусов — как у achievement.status)

# 3. СКВОЗНЫЕ ПРАВИЛА ДАТ И ВРЕМЕНИ
- Текущая дата: 2026-11-06. Любая дата (DATE) ≤ 2026-11-06. Любой timestamp (created_at, changed_at, valid_from) ≤ 2026-11-06 23:59:59.
- Мероприятие «состоялось», если event_date ≤ 2026-11-06. Достижения для несостоявшихся мероприятий не создаются.
- achieved_date: event_date ≤ achieved_date ≤ min(event_date + duration_days + 30 дней, 2026-11-06).
- Возраст школьника на achieved_date: ≥10 лет для school/municipal/regional; ≥12 лет для national/international; для региональных и заключительных этапов ВсОШ ≥14 лет. Из-за этого старшие школьники имеют больше достижений за прошлые годы.
- created_at: не раньше achieved_date и не раньше registration_date; не позже 2026-11-06 23:59:59; время суток 08:00–23:00. Обычно 0–90 дней после achieved_date. Если событие было до регистрации, это ретроспективная загрузка: created_at приходится на период после registration_date.
- Проверка статуса занимает 1–14 дней. Все записи журнала должны укладываться в границу 2026-11-06 23:59:59. Если created_at + задержка выходит за границу, уменьши задержку (минимум 1 календарный день). Если даже минимальная задержка не помещается, статус достижения остаётся submitted.
- submitted: created_at в диапазоне 2026-09-07…2026-11-06 (достижение не должно «висеть» без проверки годами). confirmed/rejected: created_at любой допустимый, подчиняющийся правилу выше.

Не сочетай код и название наугад: если не уверен, что код соответствует названию, выбери другое направление, в котором уверен. Институты — реальные названия институтов и факультетов УУНиТ (≤100 символов). Покрытие профилей: IT и информационная безопасность ≥8, инженерные ≥6, математика и физика ≥4, химия, биология и экология ≥4, экономика и менеджмент ≥3, гуманитарные, педагогические и юридические ≥4.
Скрытый профиль каждого направления (для 4.10 и 4.11): it, math, physics, engineering, chemistry, biology, economics, humanities, pedagogy, law.

## 4.4 event_type

- По годам: 2018 — 6, 2019 — 10, 2020 — 8, 2021 — 14, 2022 — 20, 2023 — 30, 2024 — 38, 2025 — 42, 2026 — 32 (до 2026-11-06).
- Название содержит уровень или этап, тему и учебный год; оно согласуется с уровнем и типом мероприятия. Название должно соответствовать формату типа: «олимпиада» — только тип olympiad, «хакатон» — hackathon, «конференция» — conference, «чемпионат»/«соревнование» — competition, «конкурс» — contest. Примеры: «Региональный этап ВсОШ по информатике 2024/25» (regional, olympiad); «Международная олимпиада по математике» (international). Слово «студенческий» не используй: мероприятия школьные.

- Пары (name, event_date) уникальны.

## 4.6 person
- ФИО реалистичные русские, пол ≈50/50, фамилия и отчество согласованы с полом; нет двойников по (full_name, birth_date).
- birth_date от 2008-11-07 до 2015-11-06 (возраст 11–17 на 2026-11-06), основная масса 13–17 лет.
- registration_date: 2023-01-01…2026-11-06, не раньше birth_date + 10 лет; плотность растёт к 2024–2026.
- email: транслитерация ФИО + цифры на условных доменах (mail.example, student.example, school-mail.example). Уникален, формат корректен.
- phone: +7 и ровно 10 цифр, уникален. Номера случайные; возможное совпадение с реальными допустимо только как случайность, это не данные реальных людей.
- Размеры школ разные (в среднем 50 учеников, от 20 до 120); у обычных школ их больше.

## 4.7 achievement
- Ограничение: UNIQUE(person_id, event_id, kind_id).
- Категория вида ↔ формат типа мероприятия (строго): olympiad→olympiad; hackathon→hackathon; science→conference или contest; sport→competition; creative→contest или competition; volunteer→contest или competition; education→conference или contest.
- Тема: достижение допустимо, только если тема вида совпадает с темой мероприятия или вид универсальный (general). Недопустимо, например, «Олимпиада по химии» на мероприятии «ВсОШ по информатике».
- Категории достижений: olympiad ≈38%, hackathon 8%, science 14%, sport 10%, creative 10%, volunteer 6%, education 14%.
- Распределение по школьникам (≈9000): 0 достижений — 17% школьников, 1–2 — 40%, 3–5 — 28%, 6–9 — 12%, 10 и более — 3% (тяжёлый хвост, максимум ≈25). Мероприятия тоже неравномерны: массовые региональные олимпиады собирают больше участников.
- Влияние школы через school_type: у школьников lyceum и gymnasium в среднем больше достижений на человека, выше доля призовых мест и подтверждений; у secondary и boarding ниже, но они тоже иногда дают победителей и призёров. Разница заметная, но без жёсткого разделения.
- place: NULL, если prize_places=0 или нет призового места; иначе от 1 до prize_places мероприятия. Призовые места ≈18–25% достижений (доля выше у lyceum и gymnasium). Уникальность мест не требуется: в базе лишь часть участников. В командных мероприятиях часть участников одного мероприятия делит одно и то же место.
- points_awarded = ROUND_HALF_UP(base_points вида × k_уровня × k_места). k_уровня: school 0.5, municipal 0.75, regional 1.0, national 1.5, international 2.0. k_места: 1→1.0, 2→0.8, 3→0.65, остальные призовые 4–10→0.5, без места→0.3. Для rejected всегда 0 (place при этом может быть заполнен).
- Итоговые статусы: confirmed ≈70%, submitted ≈20%, rejected ≈10%. Даты и время — по разделу 3.

## 4.8 achievement_document
- Число документов на достижение: confirmed — 0: 8%, 1: 77%, 2: 15%; submitted — 0: 25%, 1: 60%, 2: 15%; rejected — 0: 50%, 1: 45%, 2: 5%.
- doc_type: diploma — только при заполненном place; certificate (сертификат участника) и reference (справка об участии) — для участия или призового места; link — ссылка на опубликованные результаты (doc_number = NULL). У остальных типов doc_number NULL примерно в 10% случаев. Номера синтетические («ДП-2025-017342»).
- issue_date: achieved_date ≤ issue_date ≤ min(дата created_at, 2026-11-06).
- file_url: уникальный, вида https://portfolio.example.org/documents/000001.pdf.
- Не использовать реальные номера дипломов и реальные URL.

## 4.9 change_log
- Первая запись каждого достижения: old_status NULL, new_status submitted, actor_role owner, changed_at = created_at, note «Достижение отправлено на проверку.»
- Для итогового confirmed или rejected: вторая запись submitted→confirmed или submitted→rejected через 1–14 дней после created_at; moderator ≈90%, system ≈10%.
- Повторная подача у ≈5% достижений (≈450, итоговый статус confirmed): NULL→submitted; submitted→rejected; rejected→submitted (owner, через 1–10 дней); submitted→confirmed (через 1–14 дней). Делай её, только если вся цепочка укладывается в границу по времени (раздел 3).
- Последняя запись журнала каждого достижения совпадает с achievement.status. Хронология строгая, все changed_at ≤ 2026-11-06 23:59:59.
- Комментарии: confirmed — «Документ проверен.», «Результат участия подтверждён.», «Достижение успешно подтверждено.»; rejected — «Не приложен подтверждающий документ.», «Не удалось подтвердить результат участия.», «Недостаточно сведений о мероприятии.», «Предоставленный документ не подтверждает достижение.», «Неверно указано занятое место.»
- Согласование с другими таблицами: «Не приложен подтверждающий документ» — только если у достижения 0 документов; «Предоставленный документ не подтверждает достижение» и «Документ проверен» — только если документов ≥1; «Неверно указано занятое место» — только если place не NULL.

## 4.10 person_direction_interest
- Каждому школьнику 1–5 интересов: 1 — 25%, 2 — 35%, 3 — 25%, 4 — 10%, 5 — 5%. Направления не повторяются, приоритеты 1..k без пропусков и повторов.
- У школьников хотя бы с одним неотклонённым достижением в ≈75% случаев направление с priority=1 соответствует доминирующей теме достижений: informatics или hackathon→it; mathematics→math/it/engineering; physics, engineering→physics/engineering; chemistry→chemistry; biology→biology; economics→economics; humanities, art→humanities/law; sport, volunteering→pedagogy/economics (менеджмент)/humanities. В остальных 25% и в остальных приоритетах предпочтения произвольные.
- added_date: registration_date ≤ added_date ≤ 2026-11-06. Для priority=1 обычно 0–30 дней после registration_date, для остальных приоритетов — позже, не раньше added_date записи с priority=1 этого школьника.

## 4.11 achievement_direction (связь «достижение учитывается для направления»)
- Связи создаются только для достижений с итоговым статусом confirmed. Для submitted и rejected связей нет.
- Число направлений на одно подтверждённое достижение: 0 — 15%, 1 — 40%, 2 — 30%, 3 — 15%. Пары (achievement_id, direction_id) не повторяются.
- relevance:
  - high — профиль направления совпадает с основной темой вида достижения (informatics или категория hackathon→it; mathematics→math; physics→physics; engineering→engineering; chemistry→chemistry; biology→biology; economics→economics; humanities, art→humanities/law; sport, volunteering→pedagogy).
  - medium — смежный профиль (informatics→math/engineering; mathematics→it/physics/engineering; physics→engineering/math; engineering→it/physics; economics→math/law; humanities→pedagogy/law; sport, volunteering→humanities/economics) либо вид general (для general — только medium, направления выбираются из интересов школьника, если они есть, иначе любые).
  - Доля high ≈ 55–65%, medium ≈ 35–45%.
- Выбор направлений: не менее 60% связей ведут на направления, которые есть среди интересов этого школьника (person_direction_interest), остальные — подходящие по профилю направления из всего справочника.
- bonus_points = MIN(10, MAX(1, ROUND_HALF_UP(points_awarded × k_rel / 10))), где k_rel: high 1.0, medium 0.5.
- Ограничение суммы: сумма bonus_points по одному школьнику и одному направлению не превышает 10 (как при реальном учёте индивидуальных достижений). Достижения обрабатываются в порядке counted_from; если лимит исчерпан, связь не создаётся, если осталась часть лимита, bonus_points снижается до остатка (≥1). Из-за лимита bonus_points может быть меньше значения по формуле, но не больше.
- counted_from — дата последней записи change_log с new_status='confirmed' для этого достижения (только дата, без времени). Дата не позже 2026-11-06.

# 5. ПОРЯДОК
Генерация (зависимости): school → study_direction → achievement_kind → event_type → event → person → achievement → achievement_document → change_log → person_direction_interest → achievement_direction. В режиме Б achievement генерируй партиями по диапазонам person_id (все достижения этих школьников сразу), а achievement_document, change_log и achievement_direction — по диапазонам achievement_id. Перед achievement выведи служебный план «person_id → число достижений». Порядок загрузки в PostgreSQL: school, study_direction, achievement_kind, event_type, person, event, person_direction_interest, achievement, achievement_direction, achievement_document, change_log.
